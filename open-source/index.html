02 · License boundary

LGPL-3.0 permits use, but it is not “no conditions.”

The repository contains the GNU Lesser General Public License version 3. The license distinguishes the covered library, an application that uses its interface, and a combined work. It includes conditions around conveying covered or modified versions, notices, license copies, source availability, and the user’s ability to replace or relink a modified covered component in applicable combined works.

Use this page as orientation, not legal advice. How LGPL-3.0 applies depends on how you use, modify, combine, and distribute Daptin. Read the repository license and the GNU text, preserve notices, document changes, and ask qualified counsel about your distribution model.

04 · Contribution path

Contribute with a reproducible change.

Start with the current behavior

Search existing issues and docs, reproduce against a named release or commit, and capture the smallest schema and request that demonstrates the problem.

State the boundary

Include database, operating system, deployment method, expected behavior, actual result, logs with secrets removed, and whether the failure survives a clean setup.

Test denial paths

Backend changes should prove not only that an allowed request works, but that unauthenticated, unauthorized, stale, malformed, or repeated operations fail correctly.

Keep docs and runtime aligned

When behavior changes, update the closest guide and examples. Avoid making a release claim from unreleased code; identify the exact evidence you tested.

05 · Ownership checklist

Self-hosting gives control and responsibility together.

  • Pin and inventory releases. Know which binary, container digest, schema, database, and dashboard version is running.
  • Test upgrades with real data. Back up database and files together, rehearse restore, and verify generated schema changes before production.
  • Harden the edge. Configure TLS, trusted proxies, request limits, secrets, database privilege, protocol exposure, and network policy for your environment.
  • Observe failure. Collect logs, health, database pressure, resource use, queue behavior, and audit records without treating any one signal as complete coverage.
  • Maintain a fork deliberately. If you change the runtime, track upstream, document the delta, retain build provenance, and budget for merge and security work.
