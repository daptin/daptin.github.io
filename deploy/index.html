Docker Compose

Start with a Compose example, then make persistence explicit.

The tagged repository includes a small PostgreSQL Compose example, but it uses an unpinned image, no persistent volumes, and no health check. Treat it as connection-string syntax, not a production manifest. Pin Daptin and PostgreSQL, mount database and asset storage, and probe /ping yourself. 

git clone https://github.com/daptin/daptin.git
cd daptin
cp .env.example .env
docker compose up -d
curl --fail http://127.0.0.1:6336/ping

Kubernetes status

The checked-in Kubernetes files are historical, not a starter.

At v0.12.36 the repository's Kubernetes files use deprecated extensions/v1beta1 APIs, a latest image, and a hard-coded external MySQL address. They are useful project history, not production-ready manifests.

Build current apps/v1 manifests from the installation guide, use a persistent volume or cloud store, and pin the image. For multiple instances, share the database and file storage and configure reachable Olric ports plus peer or DNS-seed discovery.

Persistence and operations

Back up the database and files as one set.

A Daptin backup is incomplete if it contains only SQL rows. Keep the database, local asset directory or cloud-store data, deployment configuration, and encryption material in the recovery plan. Restore the complete set in a separate environment before an upgrade.

Databases

Use SQLite for local development. Daptin documents MySQL and PostgreSQL for production deployments, with connection strings supplied through flags or environment variables.

Persist the local asset path or configure an rclone-backed store. The storage guide includes local files, MinIO, and AWS S3 examples.

Health checks

Release v0.12.36 exposes /ping for process liveness. Use an external database-aware readiness check before routing traffic. The /health path is the admin application, not a probe.

Monitoring →

TLS and logs

Configure certificates and HTTPS in Daptin or terminate TLS at a trusted proxy. Retain process logs and enable audit records for changes that require a history.

Production guide →

Upgrades

Back up and restore-test the database and file store before changing the Daptin image or executable. Pin the target version, watch its health checks, and keep a tested rollback artifact.

Multiple instances

Share the database and assets, configure Olric discovery, and test startup and shutdown behavior before sending traffic to several instances.
