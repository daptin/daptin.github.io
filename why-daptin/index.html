Evaluation guide

Choose Daptin when the backend should start from the model.

Daptin is strongest when several ordinary backend responsibilities must stay coherent around relational data: APIs, users, row-level access, files, actions, integrations, realtime delivery, metering, and operations. It is a platform choice, so evaluate the constraints as carefully as the feature list.

  • Broad backend surface
  • Self-hosted control
  • Explicit tradeoffs

01 · Strong fit

Daptin compounds value when the requirements connect.

Relational products with many surfaces

Your records need CRUD APIs, ownership, groups, files, events, scheduled work, provider calls, or usage limits—and those responsibilities should share one model and permission system.

Small teams building complete products

The team wants to spend effort on domain rules and user experience instead of assembling and maintaining separate services for every conventional backend concern.

Self-hosting is a requirement

Data location, network boundaries, infrastructure policy, source inspection, or long-term operational control rule out a mandatory hosted backend control plane.

Standards reduce client coupling

Applications benefit from JSON:API, GraphQL, OpenAPI discovery, WebSockets, feeds, SMTP/IMAP, FTP, or WebDAV-style access more than from a single vendor SDK.

03 · Weak fit

Do not choose Daptin only because it can expose CRUD.

A tiny, fixed service

If the whole backend is a few stable endpoints with no identity, file, automation, integration, or operations needs, a focused framework or function may be easier to understand and operate.

Non-relational data is fundamental

If graph traversal, time-series ingestion, search, event sourcing, or unstructured document storage is the primary model, use a system designed around that workload rather than forcing it through relational resources.

Every request is bespoke code

If most behavior cannot be represented by resources, permissions, actions, or integrations, the declarative runtime may add a layer without removing enough custom application code.

No capacity to self-host

Owning the runtime also means owning patches, secrets, databases, storage, TLS, backups, monitoring, incidents, upgrades, and recovery. A managed platform may be the safer organizational choice.

06 · Proof of fit

Make the decision with one vertical slice.

  1. Model one real aggregate.Choose records with a relation, owner/group access, validation, an indexed lookup, and one field that will evolve.
  2. Build one end-user path.Create, read, update, relate, and list through the same client approach the product will ship.
  3. Add one backend operation.Use an action with validation and either a database effect or an external integration; define its transaction and retry boundary.
  4. Prove denial.Test guest, wrong user, wrong group, stale token, disallowed relation, invalid payload, quota, and sensitive-file cases.
  5. Operate it.Use the intended database and storage, terminate TLS, observe health and pressure, back up, restore, upgrade, and roll back.
  6. Record the decision.List which responsibilities Daptin removes, which your team retains, the verified limits, and the exit plan.

07 · Decision

Adopt the platform for demonstrated leverage.

Choose Daptin when the vertical slice proves that a shared model and policy runtime removes meaningful backend work while preserving the control your team needs. Decline it when the application fights the resource model, when required guarantees are not demonstrated, or when operating the platform costs more than the integration it replaces.
