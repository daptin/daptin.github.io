ONE REQUEST, THE SAME SAFEGUARDS

What happens when
a client changes a record.

Every successful change has a known user, passes the relevant access and data rules, can count toward a plan, and can notify clients that are allowed to see it.

  1. 01Know the caller

    Resolve the signed-in person and their teams.

  2. 02Check access

    Confirm they may see or change this specific record.

  3. 03Check the data

    Reject missing, malformed, or invalid field values.

  4. 04Do the work

    Read or change records, answer a report, or run an operation.

  5. 05Apply the plan

    Enforce a configured limit and record billable use.

  6. 06Tell the right clients

    Publish the change to people who may read it.

DETAILS THAT MATTER IN PRACTICE

Clear interfaces and
ordinary infrastructure.

Use a standard database

Choose SQLite, MySQL, MariaDB, or PostgreSQL instead of a proprietary data store.

Apply access rules across the product

Records, relationships, actions, live topics, and connected accounts use the same users and groups.

Inspect the running API

Metadata and OpenAPI show clients which tables, fields, routes, and actions are actually available.

Turn on only what helps

GraphQL, collaborative editing, mail, FTP, and WebDAV-style routes remain optional.

Keep secrets on the server

Actions and scheduled jobs can use encrypted external credentials without sending those secrets to the frontend.

Use plain HTTP from any client

Web, mobile, server, automation, and agent clients can call Daptin without a required language SDK.
