Common backend jobs

Compare four backend patterns before you model one.

Each pattern names the records, the access boundary, the work Daptin handles, and the work that remains in your frontend.

01 / CUSTOMER PORTAL

Customer portals with isolated private workspaces.

Application
A web portal where customers open projects, file tickets, exchange documents, and see account activity.
Data model
Customer, workspace, membership, project, ticket, attachment, and activity records.
Access
A customer sees their own account. Workspace members see records assigned to that workspace. Staff groups receive support access.
Daptin handles
Sign-in, group membership, row permissions, file storage, ticket APIs, server actions, and live update events.
Frontend handles
The customer experience: navigation, project views, ticket forms, file previews, and account settings.
Starting point
Use the schema guide for records and the permission guide for workspace membership. No maintained full portal demo is listed yet.
02 / INTERNAL OPERATIONS

Internal tools with approvals and full audit history.

Application
An operations tool where staff import orders, correct records, approve exceptions, and schedule follow-up work.
Data model
Order, customer, approval, task, import batch, notification, and audit records.
Access
Operations groups read assigned orders. Managers run approval actions. Audit data remains restricted to administrators.
Daptin handles
Generated record APIs, CSV and spreadsheet import, dashboard3 record views, actions, schedules, state machines, and audit logging.
Frontend handles
Role-specific queues, review screens, exception explanations, and charts for the work the team tracks.
Starting point
Use dashboard3 to inspect the model before building focused screens. The import and action guides show the main operations.
03 / CONTENT AND ASSETS

File and content delivery with record-level access.

Application
A catalog, media library, document portal, or publishing application backed by structured records and files.
Data model
Product, collection, article, asset, document, folder, author, and publication records.
Access
Editors change drafts, reviewers approve them, signed-in customers retrieve private assets, and public records can be read without an account.
Daptin handles
Content APIs, asset columns, local or cloud-backed storage, download checks, feeds, templates, and site routes.
Frontend handles
The editing experience, catalog or article layout, media presentation, search interface, and brand-specific publishing controls.
Starting point
Use schema samples for content models. The cloud-storage guide shows local, MinIO, and S3-backed file handling.
04 / AUTHENTICATED API

A metered, authenticated API with server-held credentials.

Application
An authenticated API, AI feature, or provider gateway with per-customer plans, quotas, and connected accounts.
Data model
API key, plan, membership, usage, quota, credit, provider, model, credential, and debit records.
Access
Customers use their own key and see their own usage. Administrators configure plans and providers. Credentials remain server-side.
Daptin handles
API keys, stored credentials, OpenAPI integrations, OpenAI-compatible routing, request and token metering, quotas, and credit hooks.
Frontend handles
Key management, usage charts, plan selection, billing, model controls, and the application feature that calls the API.
Runnable examples
The metering, integration-auth, OAuth-provider, and LLM demos test the complete request paths and important failure cases.
