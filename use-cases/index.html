Use cases

Where Daptin fits.

Four examples show the application, its data and access model, what Daptin handles, and what remains in your frontend.

01 / CUSTOMER PORTAL

Customer portals and private workspaces

Application
A web portal where customers open projects, file tickets, exchange documents, and see account activity.
Data model
Customer, workspace, membership, project, ticket, attachment, and activity records.
Access
A customer sees their own account. Workspace members see records assigned to that workspace. Staff groups receive support access.
Daptin handles
Stable public record IDs and relationships, sign-in and group membership, row permissions, file storage, ticket APIs, server actions, URL limits, and table-topic live events.
Frontend handles
The customer experience: navigation, project views, ticket forms, file previews, and account settings.
Starting point
Model customers, workspaces, and membership, then test owner, member, staff, and guest access. Let Daptin carry those relationships and decisions through the backend.
02 / INTERNAL OPERATIONS

Internal operations and approvals

Application
An operations tool where staff import orders, correct records, approve exceptions, and schedule follow-up work.
Data model
Order, customer, approval, task, import batch, notification, and audit records.
Access
Operations groups read assigned orders. Managers run approval actions. Audit data remains restricted to administrators.
Daptin handles
Transaction-scoped database writes, validation, composite uniqueness, record APIs, imports, dashboard3, actions, schedules, state tracking, and record-level change history.
Frontend handles
Role-specific queues, review screens, exception explanations, and charts for the work the team tracks.
Starting point
Use dashboard3 to inspect the model before building focused screens. Then build the approval action and schedule proven follow-up work.
03 / CONTENT AND ASSETS

Content, documents, and assets

Application
A catalog, media library, document portal, or publishing application backed by structured records and files.
Data model
Product, collection, article, asset, document, folder, author, and publication records.
Access
Editors change drafts, reviewers approve them, signed-in customers retrieve private assets, and public records can be read without an account. Test non-owner asset access in the target deployment.
Daptin handles
Content APIs, asset columns and protected delivery, local or cloud-backed storage, ETags, compression-aware caching, large-file streaming, feeds, templates, and site routes.
Frontend handles
The editing experience, catalog or article layout, media presentation, search interface, and brand-specific publishing controls.
Starting point
Start with a content model, connect the intended storage, then publish and verify the site boundary.
04 / AUTHENTICATED API

Authenticated APIs and provider gateways

Application
An authenticated API, AI feature, or provider gateway with per-customer plans, quotas, and connected accounts.
Data model
API key, plan, membership, usage, quota, credit, provider, model, credential, and debit records.
Access
Customers use their own key and see their own usage. Administrators configure plans and providers. Credentials remain server-side.
Daptin handles
API keys, server-stored credentials, URL and concurrent-request limits, access rules, OpenAPI integrations, OpenAI-compatible routing, and usage metering and quotas.
Frontend handles
Key management, usage charts, plan selection, billing, model controls, and the application feature that calls the API.
Runnable examples
Run the metering, integration-auth, OAuth-provider, and LLM demos to inspect complete request paths and important refusal cases.

Add one service

Use Daptin alongside an existing backend.

You do not need to replace your application. Add Daptin as a file service, OAuth provider, connected-account gateway, metered API, mail service, or live-record channel. The frontend can call that service directly or your existing backend can call it over HTTP.
